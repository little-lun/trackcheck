用代码替代"上机打 2F"：先离线判断一条轨道能不能成立。

```bash
python -m tools.trackcheck.run                       # 电波钟 C4io，10 种子
python -m tools.trackcheck.run --seeds 30 --wave 12.5
python -m tools.trackcheck.run --html out.html
```

## 一、三层 + 三型

### 三层（按"结论可信度"分）

| 层 | 算什么 | 可信度 |
|---|---|---|
| **L1 静态** | 卡 CD / 运算量 / 阳光 | **零误差**，纯离散数学 |
| **L2 动态** | 位置 + 伤害 + 刷新 | 近似，看趋势与裕度 |
| **期望** | 磨损收支（k vs 供给） | 粗，看量级 |

### 三型（按"僵尸该怎么建模"分）★ 2026-10-18 新增

| 型 | 僵尸 | 做法 | 为什么 |
|---|---|---|---|
| **判定型** | 小丑、蹦极、投篮 | **不做模拟**，按理论查表出"可行/不可行" | 它们的问题不是"打多少伤害"，是"节奏对不对、格子配不配" |
| **模拟型** | 红眼、白眼、冰车、橄榄、舞王… | 完整 1D 模拟 | 成败取决于"走到哪、剩多少血" |
| **期望型** | 矿工、小鬼、海豚、水路铁桶 | 算每波磨损期望 k，与南瓜卡供给做差 | 单只影响小、累计才致命 |

## 三、判定型：三个结论

### 小丑（按"每路最靠前的曾"分档，wiki 控丑八定式）

电波钟的输出：

```
1 路  曾最前 2 列  → 好    冰最迟 10.0s
2 路  曾最前 6 列  → 中    走到曾射程时冰即可
3 路  曾最前 9 列  → 紧    冰最迟 4.4s，还需 5 列加喷/8 列加曾
4 路  曾最前 9 列  → 紧    同上
5 路  曾最前 6 列  → 中
6 路  曾最前 2 列  → 好
→ 整阵按最紧的一路：紧；冰最迟 4.4s 生效
```

> **为什么是水路最紧**：3/4 路的曾顶到 9 列，早爆丑（4.4s）会正好在曾的位置爆。
> 这条直接解释了为什么电波钟的轨道是"**早冰控丑**"而不是等——**4.4s 是硬红线**。

### 蹦极（两条冰杀定式）

定式① 两曾；定式② 一曾 + 一瓜 + 任意其他输出（判定框 3 行 × 5 列）。

v0.2 我漏了**伞**这条判据，报出 3-1/4-1/4-2 三格"不满足定式"。
补上伞之后：

```
3-1  → 2-2 伞覆盖 → 免疫
4-1、4-2 → 5-1 伞覆盖 → 免疫
→ 全场每个可被偷的格子都满足「伞 或 冰杀定式」= 没有偷盲
```

**蹦极的防御是两条腿：伞，或者冰杀结构。** 只查冰杀会误报。

### 投篮

```
① 伞罩底线：是（2-2 与 5-1 两把伞合起来盖住 6 路的 1~2 列）
② 投掷前击杀：否（本阵 0 炮）
→ 可行
```

第 ② 条是给 **DE.双冰无炮** 那类阵准备的：它们不靠伞，靠"冰 + 灰烬/输出在投掷前杀掉"。
所以判据不是"有没有炮"，是"**有没有能力在它投掷前击杀**"（`KILL_BEFORE_THROW`）。

## 四、期望型：磨损收支

```
单只磨损 = 血量 / 落点防御 dps × 100（啃食 dps）
k（需求） = Σ 每波磨损
供给      = (循环时长 / 南瓜CD) × 南瓜HP / 循环波数
```

电波钟跑出来（参数 ⚠️ 粗估）：k = 2393 血/波，供给 3262 血/波 → **占用 73%，撑得住**。

**矿工特判**：挖到前场时若被灰烬覆盖 → 磨损归零（`config.MINE_HIT_BY_ASH = True`）。

## 五、已跑出的结论

### 1. C4io 的硬下限 = 平均波长 12.5s（L1，零误差）

```
冰 CD 50s ÷ 4 波 = 12.5s（核/樱桃/辣椒同理）
再短一格，轨道必断
```

### 2. IO 太强，C4io 反而站不住

```
IO 强 → 血量掉得快 → 6s 就触阈值 → 波长压到 8s
8s < 12.5s → 卡 CD 断裂
```

这就是"IO 抢刷新"的定量版本：**波长掉到 12.5s 以下**。

### 3. 模拟器自己复现出"三档打法"

脆皮多 → 8s → 卡必断 → 该走"极速关不操作"；巨人多 → 20~30s → C4io 成立。

### 4. 丑抗的硬红线是 4.4s

水路曾顶到 9 列，早爆丑 4.4s 开盒 + 1.1s 爆。所以"刷新后 4.4s 内冰生效"不是建议，是**结构要求**。

### 冰车 + 冰道模型（v0.4 完成）

**冰车**
```
速度由 x 决定：x≥700 → 0.25；400≤x<700 → 0.25 - (700-x)*0.0005；x<400 → 0.10
免疫减速（_speed_of 直接返回冰车速度）
碾压判定：冰车与格中心 |Δx| ≤ 58 → 该格植物 + 南瓜一次性清零
碾压到 曾/冰瓜/双子花/玉米炮/香蒲 → **判不可行，立即终止**（机制杀）
碾压到 大喷/荷叶/南瓜 → 只记录，不终止
```

**冰道（格子属性）**
```
Cell.iced / Cell.ice_until
① 触发：冰车每 tick 按自身坐标算出所在列 → 该格 iced=True
② 不能种植物：灰烬（樱桃/核）落点若有冰道 → 无法种植，记一次"轨道断裂"
③ 辣椒烧化：辣椒炸整行 → 清空该行冰道
④ 自然消失：TTL 3000cs（⚠️ 按"撑不过 45s 长波、撑得过普通波"标定）
⑤ flag 边界：w1 / w10 / w20 刷新时**强制清空全场冰道**
   （你给的规则：极低概率残留，忽略）
```

### ★ 冰道模型顺手暴露的一个真问题

加上冰车以后，**每一局都在 w8~w13 被"冰车碾压 3-8/3-9 的忧郁菇"终止**。

原因不是模型错，是轨道结构：

```
C4io 的 AA'（樱桃 + 辣椒）固定在"每 4 波的第 2 波"
→ 冰车如果在别的波位进来，就没有灰烬可用
→ 冰车 1350 血，从 9 列走到 8 列只要 400cs
→ 靠 大喷 + 曾 + 冰瓜 的那点输出打不掉
→ 直接碾掉 9 列的曾
```

**这解释了笔记里那句"岸路还有车抗"** —— 车抗不是自动的，得靠**灰烬在正确的波位**。
要么把 AA' 拆开按需用（快速关的做法），要么给 9 列曾补伞/地刺。

> ⚠️ 但注意：这条结论依赖出怪脚本（冰车从 w6 起出现）。
> 真实出怪下冰车频率低得多，可能不会每局都撞上。**换真实出怪后再看这条还成不成立。**

### 关于四个视频：能拿到什么、拿不到什么

**拿不到**：逐波的刷新时刻与出怪数量。

原因：PvZ 暂停时画面**没有冻结**（背景植物、阳光都在动），
`freezedetect` 只测到 ~1 秒的静止，无法把"大量暂停"从录像时长里扣掉。
→ 录像时长（慢速 7:37 / 变速 6:06 / 快速 4:39 / 极速 4:05）**不能直接当游戏时间**。

**拿到了**：四档的完整出怪种类（用户口述，比抽帧识别可靠得多）。

**结论**：与其从画面猜，不如把"已知的机制"写死进模型。**这三条阵的知识就是这么做进去的。**

### 冰车结论（修正上一版）

上一版说"每局都被冰车碾 9 列曾"。把冰车按稀有度稀疏化（每 4 波一只）后，现象变成：

```
冰车碾 6-3 / 1-3 的冰瓜（边路，w11）
冰车碾 3-9 的忧郁菇
```

**边路挡不住冰车是结构性的**：

```
边路 4~5 列只有两个大喷（射程 5~9 列）
9 列 → 5 列 = 1600cs，两个大喷只有 28 dps → 只能打掉 448
然后 5 列大喷被碾、4 列大喷被碾 → 之后没人打
→ 冰车一路走到 3 列，碾掉冰瓜
```

所以边路冰车**只能靠灰烬**，而 C4io 的 AA' 固定在循环第 2 波 →
冰车若在别的波位进来，就只能放它碾。

> 这和"边路大喷是消耗品"是同一件事的两面：**设计上就放弃了边路的中场**，
> 只求它别走到 3 列。真正要保的是 9 列曾，而 9 列曾靠 3/4 路的曾互相支援。

### 四档跑出来的对比

## v1.2 —— 判据错了：不是"总 dps"，是"击杀时间 vs 推进时间"

> 用户指出："**这个说法有问题。曾哥是 AoE 伤害，所以 2 路具备了击杀一个红眼的能力，

### 1. 「存冰没有补充吗？慢速、变速怎么剩余存冰这么少？」

**查出两个独立原因，都不是"忘了补"：**

| # | 根因 | 证据 | 修法 |

| ① | **救场层在偷吃存冰** | 原条件是「某路有巨人越过 7 列 + 冰卡 CD 没好」。慢速饱和出怪下这**每一刻都成立**，于是每 6s 点掉一个：日志里 `w3 34.0s / w4 52.5s / 58.5s / w5 64.5s / 70.5s` —— **二十秒烧光 4 个**，之后整个 2F 补不回来 | 救场层**不再动存冰**。唯一的例外是「僵尸下一口要落在**没南瓜的 CORE 植物**上」（本阵只有 2-6 / 5-6 两个裸曾），且距上一次冰冻 >3s、距上一次救急 >15s |

### 2. 核坑记账（用户：「你并没有算坑位哦」）

一个核坑炸完要 **18000cs（180s）** 才能复用。w1 与 w11 相隔约 190s —— 刚好够共用一个坑。
中间多插一次核就多占一个坑；插两次以上，180s 窗口里同时在坑的格子数会超过可用格 → **核点不出去**。

实现三件事：

```python
KERNEL_ANCHOR = {1: (2, 9), 11: (5, 9)}     # 指定坑，w11 被冰道/核坑占了才退
_kernel_slack(w) = (下一个固定核波 - w) * avg_gap - 核CD     # ≥0 才能点
self.kernel_log                              # 逐次记：时刻 / 坑位 / 是否指定
```

报告里输出**核坑台账**（每次核的坑位与"指定/退坑"）+ **坑位峰值占用**（对比可用 9 个坑）。

> 用户：「冰车的碾压判定前沿（车头）与冰道覆盖前沿（车尾）隔了整整一格，

| 概念 | 位置 | 用途 |
|---|---|---|
| **车头** | `z.x` | 碾压判定 |

所以"种植即触发"的樱桃/辣椒可以直接种在碾压判定区。

> 说明：本模型里 `z.x` 取"车头"，因此冰道由 `z.x + 80` 的格子铺设。

## v5.2 —— 分级的正确判据、南瓜归位、阵线取最深处（2026-10-20 第八轮）

用户三条纠正，其中第一条把整个分级体系翻过来了。

### 1. 分级的判据是「**原因能不能被人类阻止**」，不是「后果有多严重」

> 用户：「确切的说控丑空窗、冰慢一拍、蹦极无冰的**结果均属于致命（L0）**。
> 比如旧报告中变速关 w19 控丑缺失，但是因为这里只是差了一个冰，为了这个冰人类会
> 设法进行更灵活的操作弄出来，所以我当时把其归入人类手感内可避免（L1）。
> 总结一下经验就是说：一个事件可以致命（L0），但是造成这个事件具备一定的原因、
> 且**人类能设法阻止这个原因**就算 L1；但是即便在最优假设下人类也**绝不可能**
> 阻止造成事件的原因或阻止事件发生，则记作 L0。」

所以每条异常的评级是两步：

```
① 这个事件的后果是什么？   → 控丑空窗 → 小丑可能炸 CORE → **事件级 L0**
② 造成它的原因能被阻止吗？ → 能 → 降为 L1；不能 → 保持 L0
```

第 ② 步落成 `_squeeze(r, w)`，按人类实际会做的事排优先级：

| # | 判据 | 结论 |
|---|---|---|
| ① | 波首还有存冰没点 | 能挤出来 |
| ② | 某张卡 3s 内就好 | 能挤出来（等两秒 / 挪一下顺序） |
| ③ | 某张卡当时是"好"的却没排上 | 能（纯粹忘了） |
| ④ | 存冰 0，且冰 / 樱桃 / 辣椒 / 核 全在 CD 深处 | **人力不可及 → L0** |

变速 w19 实测输出：

> **L1** 控丑空窗：w19（2、5 路）
> 事件本身致命，但原因可阻止：**波首还有 1 个存冰没点**。人类会为这一个冰临时改操作
> （挪上一波的冰 / 等两秒 / 换点灰烬的顺序）　后果：小丑在这一波开盒可能炸到岸路 6 列眼曾 → 直接死 CORE

同一个 w19，如果波首存冰是 0、冰卡还剩 22s，判词就会变成
「w19 这一波**怎么都挤不出来**，即便最优操作也做不到阻止，所以不能降级」→ L0。

### 2. 边路大喷 = L2；南瓜磨损 = L3

> 用户：「边路大喷死是不在设计中的（虽然确实有这个冗余，但是合理运阵下绝对不会死），
> 不算正常磨损（L3）而是能补（L2）；相反，南瓜被磨损是必然的，而且设计者也通过选卡
> 带南瓜（甚至在极速关带南瓜+南瓜（复制））来补磨损，所以这算正常磨损（L3）」

|---|---|---|---|
| 边路 5 列大喷死 | L3 | **L2** | 阵里有冗余，但"合理运阵下绝对不会死"—— 它**不在设计中**，只是能补 |

## v5.7 —— 大蒜不能跨水陆（2026-10-20 第十三轮）

> 用户：「大蒜模型错了，陆路僵尸吃大蒜不会去水路，水路僵尸吃大蒜也不会去陆路。
> PE 场地中，2-9 大蒜驱赶僵尸去 1 路，5 路大蒜驱赶僵尸去 6 路」

### 1. 错在哪

上一版抄的是"相邻两路随机二选一"的通用说法：

```python
GARLIC_SWAP = {1:(2,), 2:(1,3), 3:(2,4), 4:(3,5), 5:(4,6), 6:(5,)}   # ❌
```

`2 路 → 1 或 3`、`5 路 → 4 或 6` 里的 3 / 4 是**水池**，陆路僵尸根本下不去。
所以实际不存在"分流"，只有**唯一去向**：

```python
GARLIC_SWAP = {1:(2,), 2:(1,), 3:(4,), 4:(3,), 5:(6,), 6:(5,)}      # ✅
```

`_garlic()` 里还加了一道**按地形过滤**（`z.row in WATER_ROWS` 与目标行同类才允许），
即使表写错也翻不了车。

### 2. 这条修正改变了什么

上一版"分流"会把岸路一半压力分给水路的忧郁菇，等于**白借了一半 IO**。
改成单向之后，**岸路的量整股灌进边路** —— 这才是极速关真正的负担形态。

| 项 | 分流（错） | 单向（对） |
|---|---|---|
| 换行去向 | 1/3 路各半、4/6 路各半 | 全去 1 路 / 全去 6 路 |
| 南瓜修补 | 27.4 → 27 次/局 | **27 次/局**（持平，但压的是边路） |
| 波长 | 9.16s | **9.58s（+12%）** |
| 最高等级 | L3 | L3（CORE 仍零损失） |

实测 10 局：来源 **2 路 257 / 5 路 143**，去向 **1 路 257 / 6 路 143**，一条都没跑错。

### 3. 顺带修的三处对账问题

| 问题 | 说明 | 修法 |
|---|---|---|
| 大蒜台账 20+20=40 但总数 93 | `detail[:40]` 截断后又拿去统计来源/去向 | 引擎侧加 `by_frm` / `by_to` **全量聚合** |
| 轨道执行表的控丑手段与时间轴不一致 | `wave_ctrl` 只记 **track 排的计划**，救急层 / 维护层补发的动作没算进去（极速的存冰就是救急点的） | `report()` 里按**实际 actions** 再聚合出 `ice_act` / `ash_act`，表格与时间轴都读这套 |
| 极速卡片永远不显示 L4 | `card_html(c)` 没把 `dev` 传进去 | 卡片存 `_dev` 并传入 |
| 时间轴被大蒜刷屏 | 大蒜每波被啃碎、每波补，20 次标记铺满整行 | 归为**维护性动作**：只画棕色小点（半径 2.2），不标字母，与淡色存冰点区分 |

### 4. 本版四档（12 组/档，48 组 2F）

| 档 | 录像 | 常规波长 | 偏差 | 阳光结余 | 存冰 | 核/局 | 最高等级 |
|---|---|---|---|---|---|---|---|
| 慢速 | 15.84s | 15.41s | −3% | 9154 | 4.0/4 | 4.2 | L3 + L2（6-5 大喷被啃） |
| 变速 | 12.30s | 11.74s | −5% | 8750 | 3.6/4 | 4.0 | L1（w19 空窗） |
| 快速 | 10.24s | 9.40s | −8% | 8588 | 2.2/4 | 4.0 | L3 + L2（5-7 大喷被碾） |
| 极速 | 8.56s | 9.58s | +12% | 9944 | 4.0/4 | 0 | L3 + L4（波长偏差） |

极速 +12% 已超 L4 阈值（≥10%），所以卡片里会额外列一条「L4 模型伪影 · 波长偏差 +12%」——
这条是**模型与实战的差距**，不是打法问题：单向驱赶让边路独自吃下全部压力，

> 第二阶段第一步只做一件事：**让出怪变成可选项**。

## 怎么用

**双击**：项目根目录的 `启动出怪沙盘.bat`（会自己找 Python、起服务、开浏览器）。
关掉那个黑窗口 = 停服务。

> 这个 bat 踩过三个 Windows 的坑，改的时候别踩回去：
>
> | 坑 | 症状 | 原因 |
> |---|---|---|
> | **LF 换行** | cmd 把几行拼在一起，报一堆"不是内部或外部命令"，还夹着乱码 | `.bat` 必须是 **CRLF**；用 Python/编辑器写成 `\n` 就废了 |
> | **chcp 与文件编码不匹配** | 中文全变乱码 | 文件是 UTF-8 就必须 `chcp 65001` 并同时 `set PYTHONUTF8=1`、`set PYTHONIOENCODING=utf-8`；否则控制台按 936 解 UTF-8 字节 |
> | **SO_REUSEADDR** | 第二次双击不报错，但悄悄起了第二个实例抢同一个端口 | Windows 的 `SO_REUSEADDR` 允许两个 socket 绑同一端口（不同于 Linux）。`app.py` 里 `Server.allow_reuse_address = False` |
>
> 现在的行为：端口被占 → 只打开浏览器指向已有实例，然后正常退出（`errorlevel 0`，窗口自动关）。
> 只有真报错才 `pause` 停住给你看错误。

或者命令行：


## 关键设计

### ① 出怪可选：`KINDS_OVERRIDE`

`spawn.make_wave` 本来就只吃一个"允许种类列表"，所以不需要新机制 ——
在 `config_dianbozhong` 加一个模块级开关：

```python
KINDS_OVERRIDE = None        # None = 用 TIERS[tier]
...
allowed = KINDS_OVERRIDE if KINDS_OVERRIDE else TIERS[tier]
```

仍然是**饱和出怪**：每波填满 50 只、纯加权随机、蹦极仅旗帜波、红眼配额摊到 20 波。

### ② 自动判定节奏（选阵解）

阵解是按档位分叉的，所以先要从"出怪里有什么"推出用哪一档。
**规则从上往下读，哪个先符合就是哪个**（用户 2026-10-20 定的顺序，不能打乱）：

| # | 出怪特征 | 节奏 | 阵解 |
|---|---|---|---|
| 1 | 含红眼 **且** 含白眼 | **慢速** | 慢速 |
| 2 | 含红眼、无白眼 | **变速** | 变速 |
| 3 | 含白眼、无红眼 | **中速** | **慢速**（阵解照抄） |
| 4 | 无巨人，但有橄榄 **或** 铁桶 | **快速** | 快速 |
| 5 | 其余 | **极速** | 极速 |

排这个顺序的道理：红眼是"必须拖时间 + 必须垫材兜底"的那一档；
白眼锤子只有 3000 血、走得也更慢，压力比红眼低一档，但仍要拖时间，
所以给它一个 **中速**——阵解照抄慢速，只是灰烬更宽裕。
没有巨人时就只看"有没有硬壳"：橄榄/铁桶顶着 IO 硬推，才需要逐波控丑；
连硬壳都没有（撑杆/铁门/扶梯/跳跳/海豚/潜水那种），靠结构与 IO 就能吃，直接放羊。

**节奏 ≠ 阵解**：`中速` 只是显示用的节奏名，实际跑的是慢速那套 track
（`SOLVE_ALIAS = {'中速': '慢速'}`，`CFG.MODE` 用 solve，报告头用 tier）。

判定结果会写在每组报告的标题下（`自动判定节奏 中速 …` + 一句理由 + 阵解选卡）。
若判到极速档、出怪里又有冰车/投篮，理由里会直接写明"大蒜会被碾 → 卡槽不带大蒜，
改在 2-7 / 5-7 种大喷抬丑抗"，卡槽栏也会相应少掉大蒜这一张（见 v5.8）。

### ③ 报告复用，不重写

报告不是新写的模板 —— 直接调 `html_report.card_html(r, dev)`，
所以单组报告和 `out_report.html` 里的卡片**完全同款**（含 hover 明细、字母泳道、分级清单）。

`dev`（与录像的偏差）只在"勾的就是那四套预设"时才算 —— 自定义组合没有参照物，
硬给一个偏差会误导，所以标"自定义（无参照）"。

## 顺手修掉的两个老 bug

| bug | 现象 | 原因 |
|---|---|---|
| **扶梯从来没出过** | 极速档 20 波构成里没有扶梯 | `spawn.Z` 写的是 `'梯子'`，而 `TIERS` / `engine` / `data` 全用 `'扶梯'`，`if k not in Z: continue` 把它静默丢了 |
| 多批任务卡死 | 第一次跑完后再点"开始"，新任务永远停在"排队中" | worker 是 `for j in jobs`，只处理第一次那批；改成从 `JOBS` 里反复捞 `pending` |

修好扶梯后极速档的波长从 9.58s 回到 **8.89s（+4%）** —— 原来那个 +12% 有一部分是"少了一种僵尸"造成的。

## 界面上的几个取舍

- **勾选面板显示血量**：方便一眼判断这套出怪有多重（红眼 6000 vs 普通 270）。
- **待模拟列表可删**：加错了不用清空重来。
- **进度条用文字**：`模拟中 2 / 3`，因为单局只有 0.3~0.5s，进度条反而看不清。

  否则"先建占位、后补卡片"会让第 2 组的占位跑到第 1 组报告上面去。

### 1. 大蒜在极速关变成**有条件**的

v5.6/v5.7 把极速关的 N 一律换成大蒜 —— 那是在"极速关的出怪里没有车"这个前提下写的。
出怪变成可勾选之后这个前提就不成立了：**车会把大蒜连格子一起碾掉**，驱逐根本立不住。
用户口径（第 14 轮）：有车时"**仅仅是 2-7,5-7 种大喷**提高结构丑抗"，**不把核顶回来**。

| 极速关的出怪 | 卡槽 | 场上动作 |
|---|---|---|
| 无冰车、无投篮 | 带**大蒜**（2-9 / 5-9） | 换行把岸路小丑单向赶去边路 |
| 有冰车**或**投篮 | **不带大蒜**（也不带核） | **2-7 / 5-7 种大喷**，被碾就补 |

实现分三处，判据只有一个（出怪里有没有车）：

```python
# config_dianbozhong.py
CRUSH_KINDS = ('冰车', '投篮')
garlic_slots()      # 极速 且 无车  → [(2,9),(5,9)]，否则 []
struct_fog_slots()  # 极速 且 有车  → [(2,7),(5,7)]，否则 []
```

- `engine.Sim._tick_struct_fog()`：每 1s 看一遍 2-7 / 5-7，空了就种（大喷卡 CD 7.5s
  天然限频；冰道 / 弹坑里种不下就等）。被车碾掉下一次自然补回来，**不额外操作** ——
  这正是用户说的"5-7 被压的概率不低，被压就补"。
- `html_report.deck_for(tier, kinds)`：卡槽栏按**实际选卡**渲染，有车时少一张大蒜。
- 报告多一张「结构位大喷台账」（补种次数 / 被车碾次数），只有这一档才有内容。

实测（极速、3 seed/组，其余出怪相同）：

| 出怪 | 卡槽 | 大蒜换行（次/局） | 结构位大喷（次/局） | 其中被碾 | 跑完 |
|---|---|---|---|---|---|
| 无车 | 10 张（含大蒜） | **87 / 92 / 89** | 0 | 0 | 3/3 |
| ＋冰车 | 9 张（无大蒜） | 0 | **4 / 2 / 3** | 2 / 0 / 1 | 3/3 |
| ＋投篮 | 9 张（无大蒜） | 0 | **2 / 2 / 2** | 0 | 3/3 |

"被碾 2 次"落在 L2（不在设计内但能补）—— 判定链自己就认这个结论，不用手改分级。

### 0. 先把壳和芯拆开（这次重构，行为零变化）

原来 `app.py` 里三件事挤在一起：界面字符串、任务队列、HTTP。单文件网页版
没有 socket、也没有后台线程，硬塞进去只能复制一份代码 —— 所以按职责劈成三层：

| 模块 | 职责 | 依赖 |
|---|---|---|
| `ui.py` | 出怪清单、自动判定节奏、整页 HTML、报告打印页 | 纯字符串，无 I/O |
| `jobs.py` | 建任务 / **一步一个种子** / 汇总 / 渲染卡片 | 只调 engine |
| `app.py` | HTTP 路由 + 线程推进 + 无头打印 PDF | http.server |
| `webbridge.py` | 浏览器里的"同款 API" | Pyodide 里才 import |

关键改动是 `jobs.step()`：**一次只跑一局**。服务端是
`while step(): pass` 的后台线程；浏览器里是前端 JS 每局 `await` 一次，
顺手把进度条刷了。两边跑的是同一份代码，没有第二套逻辑。

### 1. 网页版：单个 .html，双击就能用，不需要服务器

浏览器跑不了 Python，那就把 CPython 编译成的 WebAssembly 运行时（Pyodide
0.29.5）连同 `engine/data/config/run/ui/jobs` 一起塞进一个 HTML：

```
打开 HTML → 解包/下载 Pyodide → 把 .py 源码写进虚拟文件系统
          → import tools.trackcheck.webbridge
          → 前端拦下 fetch('/api/...')，转成对 webbridge 的调用
```

页面本身**一个字都没改** —— `ui.page_html()` 打出来的还是原来那个前端，
只是把 `window.fetch` 换成了"Python 直接回答"的版本。连
`/api/pdf` 都保留：网页版回打印页 + `window.print()`，用户在浏览器里
"另存为 PDF"。

两种产物（`python -m tools.trackcheck.build_web`）：

|---|---|---|---|
| `trackcheck-v0.1.html` | **15.9 MB** | **断网可用** | 引擎（wasm + 标准库）全内置，`atob` 解码后从内存喂给 Pyodide |

#### 2.1 安装目录可选（v0.1 追加）

用户要"setup.exe 能改安装目录"。三个约束决定了实现方式：

1. **不能用 tkinter**（这个 Python 是精简版，没有 tcl/tk），也不能引第三方 GUI 库
   → 用 ctypes 调 `shell32!SHBrowseForFolderW`，就是 Windows 原生的「浏览文件夹」。
2. **默认目录这时还不存在**，而 `SHParseDisplayName` 只认已存在的路径
   → 往上找**最近的已存在祖先**当起点（通常是 `…\AppData\Local\Programs`），
   否则对话框会莫名开在"桌面/此电脑"上（这个 bug 自测时真踩到了）。
3. **卸载要认自己**，不能写死默认目录
   → `winsetup.app_dir()` 以 `sys.executable` 所在目录为准，装到 `D:\Tools\TrackCheck`
     也能从那儿卸干净。

交互流程与三种回答：

```
MessageBox(是/否/取消)  是 = 用默认目录   否 = 打开浏览文件夹   取消/× = 不装了
        ↓ 否
SHBrowseForFolderW（起在最近的已存在祖先）
        ↓ 选好
normalize_dir()   选 D:\Tools → D:\Tools\TrackCheck；选 …\TrackCheck 则原样
        ↓
MessageBox 显示**最终路径**确认 → 复制 → 快捷方式 → 注册表
```

`SHBrowseForFolderW` 的坑（都踩过一遍才跑通）：

```python
# ① 字段得用 c_void_p 再 cast：结构里写成 LPWSTR 时，
#    create_unicode_buffer 赋不进去（TypeError: c_wchar_Array_260 instead of c_wchar_p）
bi.pszDisplayName = ctypes.cast(shown, ctypes.c_void_p)
bi.lpszTitle      = ctypes.cast(ctypes.c_wchar_p(title), ctypes.c_void_p)  # 要留引用
# ② lParam 是 LPARAM，不能给 None（TypeError: cannot be interpreted as an integer）→ 给 0
# ③ 先 OleInitialize(None)，否则新式界面（BIF_NEWDIALOGSTYLE）不生效
```

命令行也支持免交互指定目录（也方便自测）：

```bat
trackcheck-v0.1-setup.exe /S                             :: 默认目录
trackcheck-v0.1-setup.exe /S /D=D:\Tools\TrackCheck      :: 指定目录（原样用，不追加）
```

## v0.2 阵解栏 —— 把"阵解"变成可编辑的积木（2026-10-20 第十六轮）

> 用户：「我打算下一步制作可交互可编辑的阵解栏。你需要解析 PE.电波钟无炮 的阵解
> 的结构是什么样的，把其中能编辑的内容都暴露出来让人编辑……可以把每一波作为一行，
> 行内可以由用户插入代表 N、A、A′、I 等等操作的积木并可以在部分积木上面编辑植物落点；
> 所放的第一组积木表示刷怪当时立即生效的操作；后面排的积木前面要放触发器……
> 可以是时间、距离、卡片 cd，可以循环，就像积木编程一样。接着展示救场层……
> 如果一个救场操作在临场判断时不行，可以依次设计多层兜底。」

### 1. 先把阵解拆开看：它不是一层，是六层

| 层 | 内容 | 原来写在哪 | 现在 |
|---|---|---|---|
| ① 阵型 | 6×9 逐格 `{植物, 南瓜, 梯}` | `ARRAY` | **未暴露**（留 v0.3，单独一屏格子表） |
| ② 节奏 | `C4io` = `N \| AA' \| I \| I`，4 拍循环 | `track()` 里的 if 分支 | ✅ 节奏系/型/拍 可换 |
| ③ 波结构 | 起手 / 旗波 / 常规 / 收尾 | `if w in (...)` | ✅ 每波一行 + 角色 |
| ④ 动作 | 18 个积木（核/模仿核/樱桃/辣椒/冰/模仿冰/存冰/种冰/种冰2/种临时冰/种大喷/窝瓜压车/窝瓜/垫材/垫材2…） | `('核', 0, (2,9))` | ✅ 可增删改 + 落点 |
| ⑤ 判定 | 卡 CD、存冰数、核坑余量、一个波长水平线、欠账状态、松弛 | `if/elif` 链 | ✅ 候选兜底链（等价 if/elif/else） |
| ⑥ 救场 | 垫材 / 窝瓜 / 救急冰 三条通道 | `_tick_rescue()` | ✅ 事件 → 多层兜底 |

### 2. 数据模型（`tools/trackcheck/plan.py`）

```json
{
  "format": "trackcheck-plan/1",
  "name": "PE.电波钟无炮",
  "rhythm": {"system": "C", "name": "C4io", "beats": ["N", "AA'", "I", "I"]},
  "waves": [
    {"w": 5, "role": "常规", "sets": [
      {"when": {"kind": "all", "of": [
                  {"kind": "card_ready", "card": "核"},
                  {"kind": "any", "of": [{"kind": "card_ready", "card": "樱桃"},
                                         {"kind": "card_ready", "card": "辣椒"}]},
                  {"kind": "kernel_slack", "cmp": ">=", "value": 0}]},
       "ops": [{"op": "核", "aim": [5, 8], "trig": {"kind": "spawn"}}]},
      {"when": {"kind": "always"},
       "ops": [{"op": "冰", "trig": {"kind": "card", "name": "冰"}}]}
    ]}
  ],
  "rescue": [
    {"id": "垫材", "cooldown": 10,
     "event": {"kind": "zombie_in_window", "rows": [6,5,1], "col": 6,
               "window": [10, 75], "min_hp": 500, "zombie": "任意"},
     "levels": [[{"op": "垫材"}], [{"op": "垫材2"}], [{"op": "窝瓜"}]]}
  ]
}
```

**语义**

- `waves[].sets` 是**候选兜底链**：从上往下第一个 `when` 成立的候选胜出，
  这就是原版 `if ok('核') and ...: N elif AA' else: I` 的等价写法；
- 候选内 `ops` 是**序列**，第一块默认 `spawn`（刷怪即刻），其余挂触发器；
- 触发器：`spawn` / `time{at}` / `after{at}` / `card{name,offset}` /
  `dist{zombie,ref,axis,cmp,value}` / `state{what,cmp,value,row}` /
  `all` `any` `not`；积木可再加 `repeat{every,times,while}` 循环；
- 救场层：`event` 判真之后，**按 layers 顺序试**，哪一层全部落地就停
  （这就是"多层兜底"，不是"下一 tick 再试"）。

### 3. 引擎侧只加了两处，老轨道一个字没改

```python
# ① 事件可以挂触发器：到点后每个 tick 求值 fire / wait / expire
self._schedule(t, name, aim, w, trig={'kind': 'dist', ...})
# ② 救场层可以由外部驱动
Sim(..., rescue_tick=plan_tick)   # plan.tick_rescue：每 tick 走规则表
```

`_norm_act()` 同时接受老格式 `(name, off, aim)` 和新格式 dict，
所以内置判定轨道（`config_dianbozhong.track`）**完全不受影响** —— 这也是
"两边同场对比"的前提。顺带把 `_tick_rescue` 里的垫材/窝瓜逻辑原样抽成
`try_stall(rows, cards)` / `try_wogua(rows)`，供积木版救场复用（行为不变）。

### 4. UI：现有页面加「阵解编辑」标签页

```
基本信息   名称 / 节奏系（C 系·P 系·S 系·自定义）/ 节奏型（C4io·C4u·C6u）/ 拍
           用这个阵解跑 · 校验 · 保存 · 导出/导入 JSON · 回到内置基线
表层轨道   左：w1~w20（角色 + 本波用到的积木 + 候选数）
```

### 5. 实测：积木版 vs 内置判定轨道（慢速/变速，3 seed）

| 档 | 轨道 | 常规波长 | 断裂 | 跑完 |
|---|---|---|---|---|
| 慢速 | 内置判定 | 15.36 / 15.65 / 15.96 s | 0 | 3/3 |
| 慢速 | **积木版** | 16.37 / 15.53 / 15.67 s | 0~13 | 3/3 |
| 变速 | 内置判定 | 11.76 / 12.67 / 11.72 s | 0 | 3/3 |
| 变速 | **积木版** | 11.23 / 11.66 / 11.01 s | 0~38 | 3/3 |

但波形、存冰、崩阵判定都对得上 —— 它是一份**能改的起点**，不是原版的复刻。

### 5.1 候选条件：回看"之前某波的某个候选发生了吗"（2026-10-20 追加）

> 用户：「增加候选触发条件：之前某波的某个候选发生了。举例说明能用到的地方：
> 标准 C4io 轨道要求我 AA′ 在同一波用，可是我如果打算拆开，第 x 波用了 A′，
> 那么我第 x+1 波需要判断第 x 波是不是只用了 A′，从而决定第 x+1 波是否用 A 而不是 I。」

新条件 `{"kind": "prev", ...}`：

```json
{"kind": "prev", "back": 1, "target": "set", "set": 0}
   上一波是否由「候选 #1」胜出
{"kind": "prev", "back": 1, "target": "set", "op": "辣椒"}
   上一波胜出的候选里是否含辣椒
{"kind": "prev", "back": 1, "target": "act", "op": "樱桃"}
   上一波里樱桃**是否真的打出去了**（被卡 CD 卡住的不算）
…再加 "negate": true 表示取反
```

`target` 为什么分两种：

| 值 | 看的是 | 用途 |
|---|---|---|
| `set` | 候选**被选中**（含哪些积木） | "这一波走的是哪条分支" |
| `act` | 引擎里**真的成功执行**的动作（`actions[].ok`） | "说了要打、结果没打出去"也算进去 |

后者才治得住拆 AA′ 的真实情形：上一波选的是 `[樱桃, 辣椒]`，但樱桃那会儿在 CD，
实际只打了辣椒 —— 只看 `set` 会误判成"AA′ 齐了"，`act` 才看得见"只打了 A′"。

实现：`compile_plan()` 里带一份**属于这次运行**的 `hist`（`w1` 清空），
记录每波胜出的候选序号与积木名；引擎在 `ctx` 里多给一项 `ops_by_wave`
（由 `self.actions` 里 `ok=True` 的条目按波聚合），供 `target='act'` 用。
`prev` 只出现在**候选条件**里（触发器列表里没有它）—— 它是"这一波选哪条分支"的问句，
不是"这一块什么时候落"的问句。

配套给的示例阵解 `plans/示例 · C4io 拆开 AA′.json`（UI 里「✦ 载入示例」一键载入）：

```
w5  候选1 核（核+樱桃+辣椒都好）     ← 双卡齐，照标准 C4io 一起打
    候选2 辣椒（辣椒好了）           ← 只有 A′，先打 A′
    候选3 樱桃（樱桃好了）
    候选4 存冰
w9  候选1 当〔上一波 act 含辣椒〕且〔上一波 act 不含樱桃〕→ 樱桃   ← 补上欠的 A
    候选2 核 / 候选3 存冰（原节奏）
```

实测（慢速，3 seed）：**w6 只打出了辣椒 → w7 自动补樱桃**（`w7: ['樱桃', …]`），
波形 16.52 / 15.42 / 15.34 s，存冰 4/4，无崩阵；把 w1 的辣椒用触发器卡死之后，
下一波正确落到 `存冰` 分支，说明"没打成"也能被识别。

### 6. 已知限制

- **阵型层还没暴露**（6×9 格子表）：它属于"阵型"不是"轨道"，单独一屏更清楚，
  留到 v0.3；现在改阵型仍然走 `config_dianbozhong.ARRAY`。
- 积木版**不是**原版判定轨道的逐位克隆（见第 5 节）。
- 网页版（单文件 HTML）能编、能校验、能跑，但**不能存盘**（没有文件系统），
  保存请用「导出 JSON」；桌面版才有「保存」写进 `tools/trackcheck/plans/`。

## v0.3 阵解栏：选卡 / 全场判定 / 简化救场 / 批量编辑 / 匹配（2026-10-21 第十七轮）

> 用户九条需求 + 两条调整。核心诉求是**统一说法**：阵解里只写植物名，
> 不再有"点存冰 / 补存冰 / 查存冰数"这些过程术语。

### 1. 统一说法（本次最重要的一条）

| 旧说法 | 现在怎么写 | 引擎里对应 |
|---|---|---|
| 点存冰 | 在 **3-2 种咖啡豆** | `咖啡豆` + `aim`（唤醒那格睡着的寒冰菇 → 立刻冰冻） |
| 补存冰 | 在 **3-2 种寒冰菇** | `寒冰菇` + `aim`（落点是存冰位 → 就变成存冰，不冻） |
| 种临时冰 | 在 **2-7 种寒冰菇** | 同上 |
| 查存冰数 | **场上寒冰菇数量** / **某格是什么植物** | `plant_count` / `cell_is` |
| 垫材 / 垫材2 | **小喷菇 / 花盆** | 同名卡 |

积木目录（`plan.OPS`）全部改成植物名：毁灭菇 / 模仿毁灭菇 / 樱桃 / 辣椒 /
寒冰菇 / 模仿寒冰菇 / 咖啡豆 / 窝瓜 / 小喷菇 / 花盆 / 南瓜 / 大蒜 / 大喷菇 /
忧郁菇 / 荷叶 / 保护伞 / 双子花 / 玉米炮，另加一个特技 `窝瓜压车`
（"在 5-9 种窝瓜"的定时版）。

引擎侧只在 `do_action` 入口做一次**旧名 → 植物名**映射（`_OP_ALIAS`），
所以 v0.2 及更早的阵解 JSON 仍然能跑；`_norm_act` 也做同样映射，
于是报告、`prev` 条件、机会性动作统计看到的都是植物名。

`寒冰菇` 的三种落点写法：

```
aim = [3, 2]    → 种在 3-2（存冰位 = 补存冰；普通格子 = 种下即冻）
aim = "stock"   → 自动挑一格空着的永久存冰位（3-2 / 3-3 / 4-3 / 5-3）
aim = "temp"    → 自动挑一格空着的前场临时位（2-7 / 5-7）
aim = null      → 当场种下即冻（"冰卡"本来的用法）
```

### 2. 选卡栏（10 槽，含模仿者）

阵解里多一个 `deck`：10 张卡。**后面所有"种什么"的下拉都只从这 10 张里出**
（`plOps()` 按 `card_key` 过滤），不在卡里的积木会在列表里标红、校验时报
「不在选卡里 —— 这一块永远打不出去」。

### 3. 全场判定层（`globals[]`）

```json
{"id":"补存冰","enabled":true,"every":50,"cooldown":0,
 "when": {"kind":"all","of":[
   {"kind":"card_ready","card":"寒冰菇"},
   {"kind":"any","of":[{"kind":"cell_is","row":3,"col":2,"plant":""},
                       {"kind":"cell_is","row":3,"col":3,"plant":""}]}]},
 "ops": [{"op":"寒冰菇","aim":"stock"}]}
```

引擎每 tick 调一次 `globals_tick(sim)`（`Sim.__init__` 新增参数），
`every` 控制"隔多少 cs 才判一次"，成立就把 `ops` 依次做掉。

### 4. 简化救场层（`rescue_simple`）

用户只交**资源**和**要保的目标**：

```json
{"enabled": true,
 "resources": [{"op":"小喷菇"},{"op":"花盆"},{"op":"窝瓜"}],
 "targets": [{"id":"2-6 曾哥","protect":{"row":2,"col":6},
              "urgency_cells":0,"priority":100,"cooldown":60}]}
```

- `urgency_cells`：僵尸距它还有几格就开始救（0 = 贴脸才救，1 = 差一格就救）
- `priority`：都在危险里时谁先救（大的先）
- 打法完全由内部决定：按 `resources` 顺序试，用不了（CD / 没位置）就换下一份；
  一份都用不了就退避 30cs 再看（避免每 tick 空转刷出成吨"断裂"）

实现上补了两个引擎能力：
- `Sim.stall_at(rc, cards)`：**在指定格子**下垫材（以前只能下在固定的 STALL_SLOTS）
- 简化救场先试固定垫材位，不行就把小喷菇/花盆直接种到僵尸前面那一格

详细救场栏原样保留（第三块面板），两者可以同时开。

### 5. 快捷布置 / 波次平移 / 批量编辑

**快捷布置**：填 `N|AA'|I|I` → 解析成 `[[毁灭菇],[樱桃,辣椒],[寒冰菇],[寒冰菇]]`
→ 循环铺到 w2~w20 的**常规波**（跳过旗波 w10/w20）→ 落点/时机/兜底留空。
实现 `plan.quick_layout()` + `/api/plan/quick`。

**波次平移**：勾选波次 → `plan.shift_waves()` 把内容整体搬到 w±1；
目标波也在选区里就是整块平移，不在就被覆盖（有撤销）。
**批量**：复制 / 粘贴 / 清空走 `plan.batch_edit()`；前端有 40 步撤销栈。

### 6. JSON 格式说明（i 按钮）

`plan.spec_text(what)` 生成三种说明：`plan` / `spawn` / `config`，
通过 `/api/spec?what=` 取。页面里所有出现 JSON 的地方都有一个小 `i`
（阵解库标题、选卡、全场判定、出怪列表标题），点开是模态框，
可以**复制全文**、**下载 .md** —— 就是给"把说明 + 自然语言运阵描述交给 AI"用的。
说明里带一段「自然语言 → JSON」的对照例子。

### 7. 多套阵解 + 匹配（`trackcheck-config/1`）

阵解库可以放多套；「阵解 ↔ 出怪 匹配」表把每个出怪组绑定到一个阵解
（`queue[i].planId`），运行页会按这张表组装 job：

```json
{"format":"trackcheck-config/1",
 "spawns":[{"name":"慢速A","kinds":[...],"seeds":1,"planId":"p1"}],
 "plans":[{"id":"p1","name":"PE.电波钟无炮","plan":{...}}]}
```

「导出全场配置」/「导入全场配置」一键带走/恢复出怪列表 + 阵解库 + 绑定关系。

### 8. 两条调整

1. **只有 w1 是起手**：`role_of()` 里 w2 / w11 / w12 都归「常规」
   （引擎 `wave_ctrl['role']` 同步改）。快捷布置因此也会填 w2 / w11 / w12。
2. **取消「出怪沙盘」的开始按钮**：页面变成 ① 出怪 → ② 阵解 → ③ 运行，
   开始按钮只在 ③，且那里会先列出"哪组出怪用哪套阵解"。

### 5. 咖啡豆 / 蘑菇睡觉

用户两轮口径合起来是一条完整规则：

| 情形 | 状态 |
|---|---|
| **阵图里本来就是醒的**（忧郁菇 / 大喷菇 / 磁力菇 …） | **永远醒着**，照常工作 |
| **阵图里的寒冰菇**（= 存冰） | **睡着** |
| **运行时新种下的任何蘑菇**（白天 / 晚上都一样） | **一定是睡着的** |
| 被咖啡豆唤醒之后 | **永远醒着**，不会到点又睡回去 |

- 实现：`Cell.awake`；阵图初始化按 `data.SLEEPING_AT_START = {寒冰菇, 存冰}` 判，
  运行时一律走 `Sim._plant_into(cell, name)` —— 名字在 `data.MUSHROOMS` 里就置 `awake=False`
- 咖啡豆 `activate_ice(rc)` 能唤醒**任意格**的睡菇：唤醒寒冰菇 → 全场冰冻；
  唤醒别的蘑菇 → 只是让它开始工作
- **后果（有意为之）**：`种下即冻` / `种下即炸` 在模型里做不到；阵解里若要用
  `大喷菇` 这类"临时补种"的蘑菇，必须在同一格再排一颗 `咖啡豆`。
  受此影响，快速档从 952/920 → **958/925**（w9 那株补种的大喷不会自己醒了），
  慢速 / 变速 / 极速不变（它们不跑"临时补种蘑菇"）

### 3. PvZ Tools 旧格式（破译结果）

用户给的字符串是**明文 CSV**，比 Toolkit 的 Base64+zlib 可读得多：

```
钉耙行,ID 行 列 awake f5 f6, ID 行 列 …      （ID 是十六进制 SeedType）
```

| 字段 | 含义 |
|---|---|
| `ID` | 十六进制 **SeedType**：`2A`=42 忧郁菇、`10`=16 睡莲、`29`=41 双子花、`2C`=44 冰瓜、`2B`=43 香蒲、`25`=37 保护伞、`A`=10 大喷菇、`E`=14 寒冰菇、`21`=33 花盆 |
| 第 2、3 位 | 行、列 |
| 第 4 位 | **awake**：只对蘑菇有意义（忧郁菇/大喷菇 = 1、寒冰菇存冰 = 0），非蘑菇一律写 0 |
| 第 5、6 位 | 样本里恒为 0（未知位，原样保留） |
| `1E` = 30 | **南瓜壳**（单独一条，跟在主植物后面） |
| `30` = 48 | **梯子**（不是模仿者！） |

**「30 = 梯子」的破译依据**：用户的串里 `30` 恰好只出现在 1-2 / 1-3 / 2-2 / 2-3 四格，
正好与本库阵图的四个梯子南瓜位置**完全一致**；而「模仿南瓜」只可能有一张，不可能出现四次。

条目顺序 = 睡莲/花盆 → 主植物 → 南瓜 → 梯子（= RFC1437 §7 的推荐种植顺序）。

**验证**：用户串（1085 字符）解码出 40 格，与 `CFG.ARRAY` 逐格比对**只差 2 格** ——
3-4、4-6 两格香蒲的原串里没有写睡莲。再编码回去 = 原串 **+ `10 3 4` / `10 4 6` 两条睡莲**
（共 1111 字符，等价于 `CFG.ARRAY` 的编码结果）。

> ⚠️ 0.2.3 的文档曾写"再编码与原文逐字一致"——**那是错的**：编码器会按规则补上
> 缺的睡莲，所以会多出 2 条。真正的结论是「解出来的内容与原文完全对应，
> 多出来的只有 2 张按规则补的睡莲」（0.2.4 已改正文档与测试）。

> 顺带修了一个漏项：`忧郁菇` 之前不在 `data.MUSHROOMS` 里 → awake 位写出来是 0，
> 和工具对不上。

## 0.2.4 —— 底座可选 / 玉米炮 1×2 占格（2026-10-22 第二十二轮）

> 用户两条改进：
> ① 水路、屋顶**即使是空地**也可以勾选要不要放底座（解除底座锁定），也可以套南瓜 / 搭梯；

### 1. 底座从"无条件强制"改成"按内容强制"

| 格子 | 允许的底座 | 什么时候必须 |
|---|---|---|
| 水路（PE/FE 第 3、4 路） | 睡莲（唯一） | 有植物 / 套南瓜 / 搭梯 / 是玉米炮 → **锁定勾上**；真空地 → 随便 |
| 屋顶（RE 全部） | 花盆（唯一） | 同上 |
| 草地 | 花盆（**不能放睡莲**） | 草地本来就不需要底座，花盆可有可无 |

实现：`layout.base_name()` / `needs_base()` / `base_locked()`，

```python
if 有植物 or 南瓜 or 梯子:  水上/屋顶 → base = 睡莲 / 花盆

草地:                        base 若是睡莲 → 清成 None
```

### 2. 玉米炮 1×2

- **头格** = 你点的那格（本体）；**尾格** = 右边一格（列号 +1，与 `engine.Cell.tail` 一致）
- 图上尾格画成虚框 + 「炮尾」，点进去只显示一行红字「这格被 3-4 的玉米炮占着」，**没有主植物下拉**
- 水路 / 屋顶：**头尾两格都锁定有底座**，生成字符串时自动补（`10 3 4`、`10 3 5`）
- **南瓜 / 梯子两个勾选框锁死**（文案「套南瓜（玉米炮不能套）」）
- 第 9 列**放不下**（尾格越界 → 弹窗提示并回退）
- 改主植物时的连锁：选玉米炮 → 自动清掉南瓜/梯子、补底座、**把尾格里原来的植物清掉**；
  「整行套南瓜」会跳过玉米炮头尾
- 导入字符串后也会跑一遍同样的校正（`lyNormalizeRules()`，并提示「已按底座 / 玉米炮规则校正 N 处」）

> 引擎侧没改：`layout.to_engine()` 照旧只给 `plant/pumpkin/ladder`，
> 玉米炮的尾格由 `engine.Sim` 自己按 `span=2` 标出来；底座对引擎无意义（`Field.base_for` 另算）。

### 3. 顺带改正一处文档错误

### 0.2.6 修正（2026-10-22）

> 用户：**`[场地].名字` 是「阵型」的命名，应该放在「① 阵容布置」栏**。
> 0.2.3 时把它做在了「③ 阵解编辑」的名字上 —— 位置错了。

- **「① 阵容布置」第 1 栏改成「场地 · 阵型名」**：左边是 `[场地].`（由 app 自动生成，
  只读灰色标签），右边填裸名字（`电波钟无炮`）；换场地时前缀立刻跟着变
  （`[PE].电波钟无炮` → `[RE].电波钟无炮`）

  「运行与报告」里每组报告的头上都会显示 `阵型：[PE].电波钟无炮`
