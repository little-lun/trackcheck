# 03 · 核心：轨道语言与运算量

> 轨道理论 = 植吧为 EL（Endless）玩法发明的一套**交流语言 + 研究工具**。
> 灵感来自影音编辑软件的"视频轨道 / 音频轨道"：不同植物在不同轨道上，以时间为序各司其职。
> 来源：旧读本第 2 章（语言与工具）、4.11（OT/ET）、5.4（新工具）；新读本第 1 篇 6.2（运算量）。

---

## 一、一句话定义

> **轨道 = 阵型 + 循环 + 操作** 的浓缩记录。
> 它回答三个问题：**这是哪个阵（name）／打什么节奏（parameter）／什么时候干什么（timeline）**。

---

## 二、运算量：整个体系的根

### 2.1 定义

由刷新规律抽象出的数字。核心设定：

> **一次覆盖 4 行以上僵尸大部队的灰烬操作，会导致一次僵尸刷新。**

### 2.2 基本公式

```
2 个运算量 = 刷新 1 波僵尸
```

这里的运算量既包括**操作产生的**，也包括**植物自然输出（IO）转化来的**。

### 2.3 各操作的运算量

| 符号 | 操作 | 运算量 | 备注 |
|---|---|---|---|
| **P** | 玉米加农炮（春哥） | **1** | 最多覆盖 3 行，所以 2 炮才够 |
| **N** | 核蘑菇（毁灭菇） | **2** | 覆盖 >3 行；**若在边路只算 1** |
| **I** | 冰蘑菇（寒冰菇） | **0** | 只减速，不杀 |
| **A** | 樱桃 / 辣椒 | **1** | 若用于刷新记 1，仅减压记 0 |
| **a** | 窝瓜 | **1** | 同上；也可记 0.5 视语境 |
| **C** | 垫材 | **0** | — |
| **IO** | 自然输出达标 | **1** | 植物持续输出自行刷新的部分 |
| **+1S** | 定态单边加速 | **1** | 特定弱僵尸组合下 1 个运算量也会刷（见 §五） |
| **S / B / D** | 同步炮 / 提前炮 / 延迟炮 | **1** | 与 P 同 |
| **d** | 尾炸炮 | **1** | 小写 d |

> **记忆锚点**：核 = 2 炮。所以"核代 P6"就是用 1 个核换掉 2 门炮的位置。

### 2.4 用途

1. **验算阵型是否够输出**：
   - 最可靠的算法：**逐波数**——一个循环刷了 N 波，就需要 N × 2 个基础运算量。
   - 旧读本 5.4.1 另给了一个经验式 `参数 × 2 ≈ 基础运算量`，用于快速估算。
     ⚠️ 该式并非处处成立（书中 RE.二十炮 ch6-36s 的例子，参数 6 但实际基础运算量只有 8）。
     **估算可以用，拍板必须逐波数。**
2. **判断能不能刷**：≥2 → 一定刷；1 → 看脸；0 → 不刷。

### 2.5 基础运算量 vs 附加运算量（旧读本 5.4.1）

| 类型 | 目的 | 记在哪 |
|---|---|---|
| **基础运算量** | 激活刷新僵尸 | MT 轨 |
| **附加运算量** | 保护阵型完整（拦截小鬼、清撑杆、防红眼砸炮） | AT 轨 |

超多炮的本质：**附加运算量远超基础运算量的波动轨道**。
例：菌菌的 C2 八炮 —— 四门炮永远在刷新（基础），四门炮永远在拦截（附加）。

## 三、符号表（完整）

### 3.1 操作语言

| 符号 | 含义 |
|---|---|
| `P` | 正常用炮 |
| `S` | 同步炮（与 P 接近同时，应对同一波） |
| `B` | 提前炮 |
| `D` | 延迟炮（空炸/拦截，大写） |
| `d` | 尾炸炮（小写，P 生效后约 2.3s 生效） |
| `N` | 核蘑菇；`N'` = 复制核 |
| `I` | 冰蘑菇；`I'` = 复制冰 |
| `A` | 樱桃；`A'` = 辣椒（部分文献相反，看上下文声明） |
| `a` | 窝瓜（★ 2026-10-25 用户更正：原来写 `W`） |
| `c` | 一般用途的**垫材**（默认小喷菇）★ 硬性规定 |
| `C` | **地刺**（★ 2026-10-25 硬性规定；旧写法 `C` = 小喷菇已作废，`C'` 保留为花盆） |
| `p` | 铲种炮（挖了重种） |

> ✅ **A/A' 的约定已统一**（维基《技术:节奏体系》2021 修正方案）：
> **`A` = 樱桃，`A'` = 辣椒，`a` = 窝瓜，`N` = 核，`N'` = 复制核。**
> 旧读本里的 `A1 = 辣椒` 是历史写法，见到时换算即可。
> **`c` = 垫材**（小写；旧读本写 `C`，工具里两种都认）。

### 3.2 结构符号（操作轴专用）

| 符号 | 名称 | 含义 |
|---|---|---|
| `\|` | **隔离符** | 区分不同波次刷新的僵尸 |
| `-` | **刷新符** | 区分同一波中的过渡/刷新操作；**`-` 之前的操作不会导致刷新** |
| `/` | **分场符** | 区分上下半场在同一时机的不同步操作 |
| `~` | **波动符** | 串联两个基础节奏，说明实战在两套之间摆动 |
| `(t1\|t2\|…)` | 波长串 | 每波到下波的刷新间隔（秒或 cs） |

### 3.3 简写与复写

```
经典八炮：  P4： PP|PP|PP|PP   （复写）   →   P|P|P|P   （简写）
双冰十六炮：ch6：PPDD|IPP-PP|PPDD|IPP-PP （复写） → PD|IP-P|PD|IP-P （简写）
```
**原则**：对称操作可以只写一半。看到 `P|P|P|P` 要知道它背后是 4 对炮。

### 3.4 ★ 炮符号（节奏角色）与落点策略（怎么算落点）是**两件事**

> ★ 2026-10-25 用户纠正：原稿把 `S` 当"分离炮"是**错的**。
> `S` 是**同步炮**；"分离炮"是一种**落点/功能**，与符号解耦。
> 复写 / 简写只对炮操作有影响（一次写 = 一对炮）。

| 符号 | 名称 | 含义 |
|---|---|---|
| `P` | **主炮** | 逻辑和节奏上作为其它炮操作的**锚定基准** |
| `S` | **同步炮** | 与主炮**同时**生效；逻辑上必须锚定一个主炮 |
| `B` | **提前炮** | 比主炮生效**早**一点；功能上往往是**分离炮** |
| `D` | **延迟炮** | 比主炮生效**晚**一点；功能上往往是**拦截炮**（炸空中小鬼） |
| `d` | **尾炸炮** | 比 `D` 更晚；击杀**已落地但还没开始啃植物**的小鬼 |
| `p` | **铲种炮** | 铲掉再种回来**刷新炮冷却**；要求选卡带"炮套件（玉米投手 + 玉米炮）" |

对应的**落点策略**（`aim = [行, 策略]`，与符号独立选）：

| 策略 | 名称 | 用途 |
|---|---|---|
| `front` | 滑动落点 | 按该路最靠前那只自动挑列（`P` / `d` 默认） |
| `dyn` | 分离炮动态落点 | 选行 + 选僵尸种类，列上滑动保证它们全被炸死（`B` 常用） |
| `imp` | 拦截动态落点（空中小鬼） | 按"炸死空中小鬼"运行时求解（`D` 常用） |
| `tail` | 尾炸落点（已落地的小鬼） | 炸刚落地、还没开啃的小鬼（`d` 常用） |

### 3.5 ★ 冰变奏（冰代奏）复合符号 `PI1` / `PI2` / `PI3` / `cI4`

> 来源：[攻略:冰代奏](https://wiki.pvz1.com/doku.php?id=攻略:冰代奏) +
> [技术:精确数据](https://wiki.pvz1.com/doku.php?id=技术:精确数据)「寒冰菇取消投掷小鬼」
>
> 冰显然不能直接代炮，但可以作为**复合运算**的一部分 —— 往往能达到甚至超过一对炮的效果。

**复合符号的字符紧挨着**，整体当一个记号（`PI1` 不是 `P` + `I1`）。
四种冰代奏与符号的对应：

| 符号 | 名称 | 冰生效时机 | 目的 |
|---|---|---|---|
| `PI1` | **ICE1** | 本波 **226~601cs** 生效，常用 **360** | 冻住撑杆并拖延巨人 —— "舞王撑杆不同收"的解决方案之一 |
| `PI2` | **ICE2** | **通常与炮同步生效**；原速巨人不晚于炮 **105cs**、减速不晚于 **210cs** | 冻住**正在投掷**的巨人，并在它投出小鬼前**瞬杀**。常见形式 `PI2\|PSD`：前一波 ICE2 冻住的投掷巨人被下一波的 P 击杀、下一波投掷被 D 拦截。**由于巨人解冻时间不一，是无法拦截的** |
| `PI3` | **ICE3** | 原速**炮生效 106cs 后**冰生效（减速 **211cs**）；灰烬接 ICE3 延迟 −1 | ICE2 的升级版，**利用 bug 取消小鬼生成** → 巨人解冻后收手并重新投掷，比 ICE2 额外拖 **284cs**。**只有 1cs 有效时机** |
| `cI4` | **ICE4** | 原速**巨人垫材种植 134cs 后**冰生效（减速 **266cs**） | 与 ICE3 原理相同，**取消锤击生效** → 解冻后收手并重新锤击。**至今没有任何可应用的阵型** |

**ICE3 的机制**（《精确数据》）：巨人投掷小鬼时，若**投掷出手的那一瞬间**受冰
（时机即上表 ICE3 那一行），投掷会被**取消**，解冻后收手并重新投掷小鬼。
ICE4 同理，只是取消的是**锤击**。

**注意事项**（必须记住）：
- **ICE4 至今没人开发出可以应用的阵，看到它就该警告**。
- **ICE3 的操作精确度过高（有效时机只有 1cs）**，AvZ 出现之前无法稳定键控；
  一次选卡 17 次 ICE3 的椭盘十四炮需要 7 段拼接才录得出来 → 使用时应提示风险。

**这在工具里怎么落**（v0.3.7 起）：
快捷布置把复合符号落成「寒冰菇积木 + 对应触发器」——
`PI1` → `time at 360`，`PI2` / `PI3` / `cI4` → `after at 0 / 106 / 134`（相对上一块积木），
并给积木打 `ice_var`（`ICE1`~`ICE4`）供界面显示与告警。
手工加也一样：冰积木上有一个「冰变奏」下拉，选完自动改写触发器。

## 四、轨（记录位置）与式（记录格式）

### 4.1 两代轨

#### 第一代：**效果轨**（按植物分类，记录"什么植物做了什么"）

| 轨名 | 全称 | 内容 |
|---|---|---|
| **MA** | 主炮轨 | 用炮操作 |
| **MB** | 对称炮轨 | 与 MA 同时、落点对称的炮 |
| **PT** | 加法卡轨 | A 和 N 的加法操作 |
| **MT** | 减法卡轨 | I 的减法操作 |
| **CT** | 垫材卡轨 | C 的垫材操作 |

#### 第二代：**操作轨**（按目的分类，记录"为什么做"）

| 轨名 | 全称 | 内容 |
|---|---|---|
| **MT (MA/MB)** | 主要轨道 | 刷新操作（基础运算量）；用于刷新的 N/A 也记这里 |
| **AT (A2/A3…)** | 附加轨道 | 除刷新外的所有加法操作（附加运算量） |
| **CT** | 变奏轨道 | **只有冰变奏的用冰**记这里 |
| **ST** | 停滞轨道 | 除变奏用冰外的减法操作：冰减压、垫材、ICE1/ICE2 |

操作的四种目的（旧读本 5.4.2）：

```
1. 刷新操作（加法）→ 基础运算量 → MT
2. 附加操作（加法）→ 附加运算量 → AT
3. 变奏操作（减法）→ 变奏          → CT
4. 停滞操作（减法）→ 停滞/减缓      → ST
```

### 4.2 式（三段式）

```
Name:      [场地].阵名
Parameter: 节奏参数
Timeline:  时间轴（简式或展开式）
```

**简式**（竖线分隔每个操作时机）：
```
C6u-54s：P|I|P|I|P|N
```

**展开式**（各操作进轨）：
```
Name:      [FE].神之四炮
Parameter: c6u-54s
MT: ...
CT: ...
```

## 五、OT 与 ET：两条"世界线"

| 轴 | 全称 | 记录的是 | 适用 |
|---|---|---|---|
| **OT** | Operation Timeline | **我什么时候操作** | 高精度阵型、键控/读内存 |
| **ET** | Effectiveness Timeline | **我的操作什么时候生效** | 低精度阵型、手打 |

> "操作时间一定会对应一个生效时间，两者身处不同的世界线。绝大多数情况下成双呼应，却永不重合。"

- 精度要求越高 → 越倾向 **OT**。
- 简单阵型手打 → **ET** 更直观（炮/卡生效"黑一片冰一屏"）。
- 读内存发炮（玉萧沙首发于"无卡无伤十炮挂机"）是 OT 大规模应用的直接推手。

**换算常数**（同一操作 OT→ET 的延迟，单位 cs）：

```
P：373    N：298    I：298（咖啡豆）    A樱桃：98    A辣椒：98    a窝瓜：181    C：0
```

⚠️ 同一篇文献中，"炮释放到爆炸"写 373~378 不等（水陆差异、屋顶上界之风）。做精确计算时**取自己场地的实测值**。

## 六、效果轨 → 操作轨 的一个实例

```
效果轨：c6u-54s：P|I|P|I|P|N        ← 看到的是"打了三次炮、两次冰、一次核"
操作轨：c6u-54s：P|I-P|I-P|N        ← 看到的是"这一波的冰和炮是同一波僵尸，`-` 前不刷新"
```

差别在于：操作轨能告诉你**哪些操作属于同一波僵尸**，这对 24 炮这种一帧定生死的阵型是必需的。

## 七、$\pm 1S$ 与"定态单边加速"

满足以下全部条件时，**一次单边加速必定刷新**：

```
① 无巨人
② 有慢速僵尸（撑杆/门板）
③ 有高血僵尸（橄榄球）
④ 至少出现 3 种快速僵尸
```

轨道中记作 `+1S`（运算量 1）。

**用途**：在动态节奏里白捡一个运算量。例（旧读本）：

```
心五炮（极速组合）ch6：P/+1S | IP-Pa | P/+1S | IP-A
```
每次双边加速清场后补一次定态单边加速，把压制强度从参数 4 提到参数 6。

> 说白了是概率问题：**僵尸越脆，刷新越稳；僵尸越皮，刷新越玄。**

## 八、★ 波长串 ↔ 操作时间：怎么对上（2026-10-24 以 FE.雾四炮 为准重解）

这一节回答一个问题：**写下 `N6s:I-PP|I-PP|N|PP(18,18,9,9)`，每一拍到底在哪个时刻发生？**

### 8.1 三条约定

```
① 一拍 = 一段时间。波长串 (g0,g1,g2,g3) 给的是**每一拍持续多久**（秒）。
② 一拍的操作发生在**这一拍的开头**（不是结尾、也不是中点）。
③ 所以第 k 拍的时刻 = g0+g1+…+g(k−1)，是**累加**，不是"第 k 拍的波长"。
```

N6s（start 取第 2 拍 = `I-PP`，因为开局没有怪可冻，第 1 拍的 I 不打）：

| 拍 | 内容 | 本拍时长 | 开头时刻（相对起手炮） |
|---|---|---|---|
| 0 | `I-PP`（I 不打） | 18s | **0** |
| 1 | `I-PP` | 18s | **18s** |
| 2 | `N` | 9s | **36s** |
| 3 | `PP` | 9s | **45s** |
| 4 | `I-PP`（下个循环） | 18s | **54s** |

→ 炮的时刻：0 / 18 / 45 / 54 / 72 / 99 / 108 …（**不是** 0/18/36/45）
→ 核的时刻：36 / 90 / 144 …

**最容易错的一点**：`(18,18,9,9)` 里那个 `9` 只管「这一拍拍完之后等多久进下一拍」，
它**不是**"这一拍的操作发生在第 9 秒"。真正的时刻永远靠累加。

### 8.2 从"波长串"到"触发器"

固定波长的阵，每一块运算量都用 `after_block` 挂在**上一波第一块运算量**上：

```json
{"op": "玉米炮", "aim": [2, "threat"], "id": "w3-1-1",
 "trig": {"kind": "after_block", "id": "w2-1-1", "delay": 900}}
```

`delay` = **上一拍持续多久**（= 波长串里上一拍的秒数 × 100）。
这样串起来的效果正是 8.1 的累加表。

> **锚点必须是"有运算量的那一块"**（炮 / 核 / 灰烬），不能锚在"刷怪即刻"的冰上。
> 冰是按刷怪时刻打的（慢波要一出来就冻），拿它当锚点等于让整条链跟着刷波走，
> 那就不是定时了。实测后果：FE.雾四炮 的炮在 w4 之后整段空窗 3400cs（4 门炮同时进 CD），
> 边路冰车正好从这段真空里碾进来。

### 8.3 一个坑：刷波不是定时的

生存无尽的波是「**本波剩余血量跌破阈值**」才刷，不是每 N 秒刷一次。所以：

- 「第 15 波的操作」要等 w15 真的刷出来才会被排期；
- 一旦前方清得慢，后面的炮就跟着迟到；
- 病态情况：炮迟到 → 杀不够 → 更晚刷波 → **炮的空窗越来越长**（实测出现过 3000 / 5600cs）。

对策（`rhythm.fixed_timeline = true`，可选）：把整局的运算量编译成一条**绝对时间轴**
（`plan._fixed_timeline`），与刷波彻底解耦；超炮产能的那几发单独丢掉并报出来
（一门炮 3475cs 装填，N 门炮在任意 3475cs 窗口内最多 N 发）。

> **默认不开**。实测：经典八炮 P4（8 炮 / 9s 一对炮）开了直接 0/20
> （绝对时刻会逼着炮在"僵尸还没进场"时开空炮，把装填浪费掉）。
> 但 **FE.雾四炮（4 炮 / 18s 慢波）开了是决定性的**：慢速档 0/10 → **10/10**。

> ★ **2026-10-25 起口径变了**：只要「快捷布置阵解」里**填了波长串**，就自动打开
> `fixed_timeline` —— **给了波长串的阵按定义就是固定波长阵**，运算量必须定时。
> 见 8.5。

### 8.5 ★ 6s 极限波长（PE.二十四炮）：链式排期会彻底崩

`P6-2i:PD|PI2|PSD|PD|PI2|PSD(6,6,6,6,6,6)`，24 门炮、6s 一波。

- **链式**（`after_block + 600`）：某一波清得慢 → 后面的拍整串迟到；更糟的是
  「第 N 拍要等 wN 真的刷出来」，刷怪一停滞就**一拍都不打**。
  实测 w10 之后完全停炮，红眼走进来把 2-7 的炮啃了 —— 0/3 全灭。
- **绝对时间轴**：与刷怪解耦 → **饱和出怪 20 波全清，6/6 全过**。

所以判据是：**只要有波长串，就走绝对时间轴**。另外两处细节也一起改了：

| 细节 | 原来 | 现在 |
|---|---|---|
| 起手定时 | 固定 `time at 900`（从 18s 波的 case 学来） | 最短波长 ≥ 9s 仍取 900；更短的取"半个波长"，下限 100cs |
| 炮的瞄准 | — | **落点没有射程限制**（玉米炮点哪打哪，1-1 的炮打 9 列合法）；R=115 只是**爆炸半径**，不是瞄准射程 |

### 8.6 ★ 波长串的单位：s 还是 cs（2026-10-25 自动识别）

写 `(9,9,9,9)` 是**秒**；写 `(875,875,875,850)` 是 **cs**。工具自己判：

| 写法 | 判据 |
|---|---|
| `875cs` / `8.75s` | 后缀写死了就听写明的 |
| 最大项 **≥ 100** | 整串是 cs（一"个"波长不可能 100 秒以上） |
| 最小项 **≥ 60** | 整串也是 cs（最短波长 6s，整串都 ≥60 秒的阵不存在） |
| 其余 | 秒 |

按 cs 读入时提示里会回显 `(875,…) → (8.75,…) 秒`。

### 8.7 ★ D（延迟炮）默认是"拦截"还是"补刀"
| 轨道里有冰？ | D 的落点策略 | 例子 |
|---|---|---|
| **有**（`PI2` / `PSD` 那类定式） | 「拦截动态落点（空中小鬼）」，三个时机 | PE.二十四炮 |
| **没有** | 「延迟补刀」：主炮之后 100cs 打同一片前排 | FE.弦十四炮 `PD\|PD\|PD\|ND` |

理由：弦十四炮 14 炮 / 34.75s 循环正好 = 3 对 P + 4 对 D（每门炮一循环打一次），
D 是**主力输出**；一拦小鬼就等于"8.75s 一波的小丑/普通波全程不开炮"，炮力掉 1/3。



### 8.3.1 ★ 一个必须记住的坑：时间轴要**延伸到 w20 之后**

对局要一直打到「20 波清干净」才算结束，而阵解只写到 w20。
按"只铺阵解里的波"来编译，最后一个炮点大约是 t=279s，
可尾兵常常活到 **340s+** —— 中间 **6570cs 一门炮都没开**，
w19/w20 的冰车就是从这段真空里碾进边路冰瓜的。

```
FE.雾四炮 慢速 seed1（修前）：
  ... 26100(2 炮) 27900(2 炮) ——然后 6570cs 真空—— 34470 崩：冰车碾压 6-3 冰瓜
```

修法：把**运算量**再多铺一轮（冰 / 咖啡豆不铺，避免白烧卡），
时间轴按 `events.sort(t)` 续上。修后 FE.雾四炮 慢速 **0/10 → 10/10**，
极速/变速/快速全部 10/10。

### 8.4 起手拍（start）

固定波长的阵「起手必然从连续节奏最快的点开始」：允许从轨道里任意一拍起铺。
N6s 从第 2 拍起铺 → `PP|N|PP|I-PP|I-PP|…`，可以连续过 3 个快波。
起手那一拍里**没有运算量的操作不打**（N6s 的 I 开局没有怪可冻）。

### 8.8 ★ 收尾（最后一波之后的尾兵）

用户口径（2026-10-25）：**「根据其血量，用所有救场卡、最后是 P 消灭所有尾兵。」**

实现在「快捷布置阵解 → 自动选卡/救场」里，自动挂一组**全场判定**：

| 规则 id | 条件 | 每 | 内容 |
|---|---|---|---|
| `收尾-辣椒` / `收尾-樱桃` / `收尾-窝瓜` | `when.kind = tail` | 200cs | 各一张灰烬（按"范围大 → 范围小"的顺序） |
| `收尾-P-低路` / `收尾-P-高路` | 同上 | 300cs | 玉米炮，落点走滑动（2 路 / 5 路各一条） |

`tail` 的判定 = **最后一波（w20）已经刷出来，且场上还活着僵尸** ——
这之后不会再有新波，卡可以放心全砸掉。

**每张卡必须各自一条规则**：`tick_globals` 遇到**第一块失败就 `break`**，
塞在一条规则里的话辣椒一进 CD 就把后面的樱桃 / 窝瓜全挡住了。

实测收益（FE.弦十四炮，饱和出怪）：0/6 → **2/6**。


用户原话：「`-` 表示前者是**刷怪立即**操作，而后者是**稍等至波长**操作」。

- 编译成 `after_block(本波第一块运算量) + 本拍波长`，并且**不进绝对时间轴**
  （它本来就该由运行期解析），用标记 `late_shot` 保住。
- ⚠️ 锚点必须是**真的排在轴上**的那一块：冰是"刷怪即刻"、不进轴，
  拿它当锚点等于永远查不到生效时刻（第一版就是这么错的）。

### 8.10 ★ `-`（刷新符）= 前者**刷新即刻**、后者锚在"上一个主运算量"上

用户口径（2026-10-25 二次澄清）：

> 「`-` 前的操作是**刷新即刻生效**（或者刷新后几十 cs），`-` 后的操作依旧是
>   **锚定上一个锚定波长的操作**（或者说是最后一个有运算量的操作）。」

所以：
- `-` **前**那一组的运算量 → 打 `spawn_shot`，**不进绝对时间轴**
  （进了就成了绝对时刻，不再是"刷新即刻"），由 `track()` 在刷怪那一刻排期；
- `-` **后**那一组是**主运算量** → 留在轴里，`after_block(上一个锚点) + 本拍波长`，
  并且它就是这一拍的**新锚点**；
- 含 `-` 的拍**不能整拍跳过**（跳过会让时间轴丢拍 —— 实测 `D5:I-PP\|I-PP\|PP`
  的炮点变成每三拍一发）。

⚠️ 反例（0.3.15 做错的方向）：把标记打在 `-` **后**那组并整拍跳过，
结果主运算量根本没进时间轴。

### 8.11 ★ 刷波**不要**和波长串强行对齐（2026-10-25 用户）

> 「本来这些轨道非常复杂的阵（尤其是极限阵）就很不稳定，
>   所以只要存在一个全出怪饱和种子过了就视为成功。」

所以模拟的刷波仍旧走"本波血量掉到 65% / 27s 窗口 / 2s 真空"那条路（见 `02-核心-僵尸刷新机制` §一·补），
**不**按波长串强制排刷波时刻（曾试过：二十四炮 6/6→5/6，本 case 也没救回来）。

### 8.12 ★ `c` = 垫材，`C` = 地刺（2026-10-25 用户**硬性规定**）

- **`c` = 一般用途的垫材**（默认小喷菇）；**`C` = 地刺**。
- 旧写法 `C` = 小喷菇已作废；`C'` 保留为「花盆」。
- 用 `rhythm.letters = {"c": "花盆"}` 之类可以逐份阵解改写（逃生口）。
- ⚠️ FE.二十四炮 那条 `C9u` 轨道里写的是小写 `c`（作者本意是地刺）；
  按本规则要改成 `C` 才会种地刺去解决冰车。


### 8.13 ★ 灰烬可以杀**地下挖掘的矿工**（2026-10-25 用户）

> 「P、N、A、A′ 是可以杀死正在地下挖掘的矿工的。落实这个逻辑以后，
>   不再需要额外处理矿工的手段。」

- `best_aim`（炮 / 樱桃 / 核都用它）统一走 `ash=True`。
- 效果：FE.弦十四炮 饱和 2/8 → **8/8**（矿工再也不是"必须留一手"的东西）。

### 8.14 ★ P 的滑动落点：覆盖全场，但**不许炸坏梯子**（2026-10-25 用户）

- 候选列 1~9 全场；`best_aim` 里另加一条硬约束：
  **判定域盖到任何"搭了梯子的格子"的候选直接判为不可行**（梯子炸掉就白搭了）。

### 8.15 ★ `C`（地刺）= **本行本波冰车全部暴毙**（2026-10-25 用户）

> 「`C` 直接使本行新出的一波冰车全部暴毙。实战中必须将地刺种在冰车下面
>   才可以杀死所有冰车，预布置地刺没法全杀冰车。」

- 结果导向（`Sim._spike_kill`）：种下去就把**现在场上有车的每一路**的车全清掉。
- 波首那一 tick 车还没出来 → 等（最多 3s），因为实战是"看到车才种"。
- 效果：FE.二十四炮（无花）的"冰车碾压"死因**完全消失**。

### 8.17 ★ 白天场的蘑菇：「装着睡着的蘑菇的格子」是**唯一**说法（2026-10-25 用户）

> 「移除所有**前场临时位 / 永久存冰位**的说法，相关内容全部移除或改造。
>   只有这一种说法：**白天场阵图中包含着睡着的某种蘑菇的格子**。
>   这个'睡着的某种蘑菇'当轨道中需要这种蘑菇时作为卡片没好时的补充；
>   而一旦这个格子因为其被使用而**变空**，就持续判定用这种蘑菇（**及其模仿**）的卡片填上。」
> 「白天场地需要用到蘑菇植物卡片时，先判断卡片 cd 有没有好：cd 好了，
>   同时种该植物与咖啡豆；否则，判定场上是否有**睡着的该种植物**，
>   有则对场上的这个植物用咖啡豆。」
> 「**这一个卡积木就完成（咖啡豆 + 蘑菇）**，放弃两个卡积木的实现方式。」

**数据结构（只有一份）**
- 阵图上写 `{"plant": "寒冰菇", "awake": false}` —— 这就是「装着睡着的冰的格子」。
  引擎里 `Sim.sleep_cells = {rc: plant}` 在开局从 `array` 里挑出这些格子（夜场为空，
  因为夜场蘑菇种下就醒）。
- 现场「还躺着几个」= 直接数 `cells` 里 `plant in MUSHROOMS and not awake` 的格子
  （`Sim._sleeping_rcs()`）。**没有** `ice_slots` / `temp_ice` 这种记账了。

**两条行为**
1. **补充**：冰卡（含模仿卡）都没转好 → `_wake_sleeping('寒冰菇')` 点场上睡着的那个；
   一个都没有才报卡手。
2. **补种**：被点掉的那一格 `cell.plant = None`（用掉了），
   `_tick_day_mushroom_refill()` 持续判定「这一格空了 + 卡转好 + 有阳光」→
   用 `_CARD_OF[plant]`（冰）或它的模仿卡把它种回去，**种回去是睡着的**。
   ⚠️ 坑：`D.CARDS` 的键是**卡片名**（`冰` / `模仿冰` / `核`），不是植物名 ——
   不过一次 `_CARD_OF` 就永远补不上（寒冰菇卡手的另一半原因就在这里）。

**一个积木做完全部逻辑**
- 冰：`_plant_ice` + `_wake_after_plant`；毁灭菇：`_day_mushroom`（豆够才扣蘑菇卡 CD）。
- 自动填充**不再**往冰/核积木后面塞一颗 `咖啡豆`；「咖啡豆」积木只用于
  「显式唤醒某一格睡着的蘑菇」。
- **不许凭空生效**：咖啡豆没好时冰就只是睡下（不 `_freeze()`）。
- `_coffee_pending` 只看 **150cs 窗口**（以前"本波动作表含咖啡豆"就算，
  一颗豆会把整波的冰都变成睡冰）。
- 辣椒位那一格如果躺着睡着的蘑菇 → 先点掉（顺带生效）再种辣椒，空出来后由补种填回。

### 8.18 ★ 简写 / 复写：`PP` 在简写模式下 = 一对（2026-10-25 用户报的 bug）

- 用户报：「选择节奏 `D5:I-PP|I-PP|PP` 后，报错至少需要 12 门炮」。
- 原因：简写模式下**每个 `P` 各自翻倍**，`PP` 变成 4 门炮。
- 正确口径（与 §3.3 的 `PPDD`（复写）= `PD`（简写）一致）：
  **简写模式下连续相同的炮字母合并成一节** → `PP` = 一对 = 2 门。
- 另：`spectrum_report(pair=…)` 用**界面当前的设置**做校验，不再只读阵解里存的那份。

### 8.19 ★ 自动填充的发炮时序（2026-10-25 用户口径）

| 位置 | 口径 |
|---|---|
| **起手** | 刷怪后**半个波长**（`time at = 本拍波长 / 2`） |
| **其它波** | `after_block(**上一波最后一个运算量操作**) + 本拍波长` |
| **收尾** | **只在 w9 / w19 / w20 生效**，不影响其它波；且收尾的 P 要等时间轴的炮全打完（`no_cob_pending`） |

实测：
- `D5:I-PP|I-PP|PP (12,12,12)` → 起手 600，之后每 1200cs（= 12s）。
- `P4:PP|PP|PP|PP (9,9,9,9)` → 起手 450，之后每 900cs。

⚠️ 坑：锚点判断不能写 `x.get('cob') in (None, 'P', 'p')` —— **冰 / 灰烬没有 `cob` 字段**，
`get` 也返回 None，于是"延迟补刀"会锚到冰上（冰是刷怪即刻、不进轴，永远等不到）。
必须显式要求 `op == '玉米炮' and cob in (None,'P','p') and not spawn_shot`。
